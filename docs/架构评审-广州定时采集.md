## 0. 结论

真正的问题是**来源发现与来源规则没有成为独立、可观测、可复用、可预算的任务**。采集频率不是主因。

三个真正的阻塞点：

1. **来源任务永远不会开始。** 入队后请求停在 `blocked/待补可复用的同版本来源模板`；领取 SQL 只会重新检查“已有 `source_bundle` 或旧版 `wiki-episode` 模板”的行，新作品没有模板，因此不会被领取，也不会触发任何来源工作。`dispatch-aired-episodes.sql:15-35`。
2. **双来源在 7 个校验点被写成硬条件。** 规则生成、规则附接、文档校验、覆盖度、规则白名单、配置登记、外部采集导入都要求“官方 + 独立”两份。最新番只有官网时，B 级单官方来源无法自动通过。
3. **规则生成在预算之外。** `source_rule` 调用使用的 subject 是 `plan:<uuid>`，而预算服务只识别 `research:` / `media:`，返回 `unmanaged`；规则既没有注册表，也没有复用、过期和成本归属。

目标架构不换技术栈：继续 Go + Gin + PostgreSQL + Pi Durable + OpenAI + systemd。最小改动是：

- 新增 3 张表：作品官方来源登记、来源规则注册表、来源任务表；
- 来源任务在晋升前独立运行，验证通过后**复用现有 `AttachSourceBundle` SQL** 把 bundle 写回制作请求；下一轮 5 集领取照常晋升，队列节奏完全不变；
- 把 7 个硬条件改成按 `mode=paired|official_only` 动态计算；
- B 级单官方来源自动通过，但只放宽“来源份数”，不放宽五维、图片和发布；
- AI-first 只改执行面：模型在 `discovering/rule/capturing` 内驱动只读工具，固定验证器保留判定权（见 0.2）；
- 先跑 FX 规则复用、药屋季偏移、罗梅莉亚嵌套 JSON，再跑单官方 B 级，最后覆盖其余缺集。

最小 MVP 见第 17 节：**1 个迁移 + 3 张表 + 1 条来源 tick + 1 个 Agent 入口 + 1 套 30 条评测集 + 7 处校验放宽 + 3 部试点**。tick 从制作请求自动生成来源任务，不新增定时器。不做搜索中台、不做新服务、不做向量库、不改发布链路、不重建已有制作任务。

### 0.1 本轮收紧的 6 处

1. **等级和模式变成输出。** A/B/C 与 `paired`/`official_only` 由 Go 的 `EvaluateEvidence` 一处计算；运维不填，模型不返回，下游只读结果。7 个校验点因此只消费 `mode`，不再各自推断。
2. **B 级写作链只加一个别名。** 新增“叙述来源”访问器，paired 取 guide，official_only 取 official；`episodeOutline`、配置 `starts`、research 提示词、人物证据检查都改用它，不在 5 处各写一个 `mode` 分支。证据仍只有官方一份，不伪造 guide 文档。
3. **去掉规则 90 天过期和 `model_reserved`。** 规则每次使用都做目标页与相邻集复验，失效当场暴露；预算用 `model_used` 上限加回执对账，不做预留。
4. **状态从 10 个收到 8 个。** `retry_wait` 并入 `queued + next_attempt_at`；`failed`、`cancelled` 并入 `closed + reason`。
5. **来源任务由制作请求生成。** 来源 tick 先跑一条幂等 INSERT，从广州队列的单集请求建任务；不依赖盘点快照，也不新增 timer。已验证来源仍是附接回同一请求。
6. **附接范围写清。** 现有 `AttachSourceBundle` 写死 `paused_reason='等待广州批次'`，MVP 只生成 `queue='gz-20-aired-20261125'` 的任务；其他队列要先把附接 SQL 参数化。

### 0.2 AI-first 定位与术语

`AI native` / `AI first` 在本报告里指两层控制面。模型不接管数据库、验证或发布。

- **持久编排面（Go）** 负责入队、状态迁移、租约、预算、验证、附接和发布。它必须确定、可恢复、可对账。
- **代理执行面（Pi/Agent）** 负责 `discovering`、`rule`、`capturing` 内部的下一步决策。模型用只读工具看页面、找候选、生成规则、调用验证器。

一句话边界：**AI first 给模型控制权，判定权留在固定程序和证据模型。**

这句话至少对应三个问题。

1. **控制权。** 术语是 `agent vs workflow`。信号是你想让模型决定下一个抓取或查询，而不是继续在 Go 里加分支。
2. **适配器维护。** 术语是 `wrapper induction` 和 `generate-and-filter`。信号是站点改版和逐集写规则是主要成本。
3. **人力与自主度。** 术语是 `human-on-the-loop`。信号是你想减少人工登记与复核。

本报告采用第 1 和第 2 个。`discovering`、`rule`、`capturing` 内改成 agent loop；队列、状态迁移、验证和提交仍是 workflow。第 3 个是运维结果，不是架构起点。

| 术语 | 一句话 | 在本项目对应 | 出处 |
| --- | --- | --- | --- |
| Agent vs workflow（代理与工作流） | 工作流由代码决定步骤，代理由模型根据观察决定下一步 | 三个阶段内用代理；队列和提交用工作流 | [Anthropic](https://www.anthropic.com/engineering/building-effective-agents) |
| Agent loop（代理循环） | 行动、读工具结果、再决定，直到满足停止条件 | 每个来源任务内的 observe→act→stop | [Anthropic](https://www.anthropic.com/engineering/building-effective-agents) |
| Tool use（工具调用） | 模型从有限工具集选择动作，应用执行并返回结构化结果 | 只读工具：`search_candidates`、`fetch_page`、`parse_json`、`check_rule`、`read_inventory` | [Anthropic](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) |
| Context engineering（上下文工程） | 每步只放最小高信号 token | 每步的页面片段、候选、验证结果和预算 | [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) |
| Generate-and-filter（生成后过滤） | 模型批量生成候选，固定测试筛掉错的 | 候选规则加 `checkEpisodeSourceRule`、相邻集和负例 | [AlphaCode](https://arxiv.org/abs/2203.07814) |
| Skill library（技能库） | 验证过的可执行技能可检索复用 | `episode_source_rules` 的 `verified` 行 | [Voyager](https://arxiv.org/abs/2305.16291) |
| Agentic RAG（代理式检索） | 代理多轮查询、读取、改写 | 来源发现的多轮 query→fetch→reformulate | [Agentic RAG 综述](https://arxiv.org/abs/2501.09136) |
| Declarative LM program + compiler（声明式程序与编译器） | 用声明式模块描述流程，用指标驱动优化 | 规则抽取模块加评测集，后续阶段再做 | [DSPy](https://arxiv.org/abs/2310.03714) |
| Structured outputs（结构化输出） | 生成受 schema 或语法约束 | 规则只能输出受限 JSON schema，禁止任意 JS | [Outlines](https://github.com/dottxt-ai/outlines) |
| Eval harness（评测集） | 固定任务集和可重复判定 | 30 个来源任务、pass@1、成本、回归 | [WebArena](https://arxiv.org/abs/2307.13854) |
| Indirect prompt injection（间接提示注入） | 网页正文可以藏指令，代理可能把数据当命令 | 页面正文标记不可信，模型工具全部只读 | [Greshake 等](https://arxiv.org/abs/2302.12173) |
| Trajectory observability（轨迹可观测） | 每步决策与工具调用记成 span | `invoke_agent`/`execute_tool` span、task id、tokens | [OpenTelemetry](https://github.com/open-telemetry/semantic-conventions/blob/v1.40.0/docs/gen-ai/gen-ai-agent-spans.md) |

相邻领域借了三个结构。

- **编译器工程。** CompCert 是 “[a high-assurance compiler](https://compcert.org/)”，带机器检查的证明。可借的是中间表示加验证器；断点是网页没有形式语义，验证只能到样本级。回来的词是 generate-and-filter、structured outputs、skill library。
- **Web 信息抽取。** Dalvi 等人的[论文](https://arxiv.org/abs/1103.2406)用 wrapper induction 处理站点模板和噪声样本。可借的是按站点维护抽取器；断点是 LLM 的泛化换来了方差和成本。回来的词是 wrapper induction、skill library、agentic RAG。
- **安全关键自主系统。** 欧盟 AI 法案[第 14 条](https://artificialintelligenceact.eu/article/14/)要求系统能被人有效监督，并按不同自主度运行。可借的是自主度分级、运行时监控和升级阈值；断点是发布公开且不可逆。回来的词是 human-on-the-loop、eval harness、trajectory observability。

原描述没提但必须补上的约束：

- **评测先于自主。** 没有固定评测集，AI first 只是把确定性换成方差。
- **注入与工具权限。** 网页正文是不可信输入，模型工具只读，写库和发布只由 Go 执行。
- **每条轨迹的预算。** token、抓取次数、墙钟时间都有上限。
- **模型与提示版本。** 模型名、提示版本、规则 SHA 写进证据，升级前后跑同一评测集。
- **不可逆动作隔离。** `publish_to_reader:false` 保持有效，模型无法触发发布。
- **升级阈值。** 只在连续失败、证据冲突或预算耗尽时找人，不设默认人工复核。
- **失败数据回流。** C 级失败变成新的评测样本，不只记一条 blocked。

改写后的描述：

> 我要把采集从固定工作流改成 AI-first 的闭环代理：模型在只读工具集里决定发现、抓取和规则合成，固定评估器负责接受或拒绝，验证过的规则进入技能库复用；用评测集、轨迹和预算约束自主行为，网页正文按不可信输入处理，发布保持关闭。

数据库是唯一事实源，Pi SQLite 只保存执行恢复状态。这个边界正确，继续保留。

### 1.2 广州队列的真实链路

1. `enqueue-aired-episodes.sql:23-38` 为 20 部作品写入 `episode_production_requests`。每条请求默认 `stage='inventory'`、`operator_paused=true`、`paused_reason='等待广州批次'`、`token_limit=60000`、`publish_to_reader:false`。
2. `folio-episode-dispatch.timer` 每 30 分钟执行 `dispatch-aired-episodes.sql`。
3. 该 SQL 先做一次补写：已有已发布计划的行直接 `local_ready`。随后计算 `has_template`：
   - `production_policy ? 'source_bundle'`，或
   - 同作品更早一集是旧版 `sourceRules->>'guide'='wiki-episode'`，且 `guide LIKE '%#ep'||template.number`，且有 `art`。
4. 只有 `stage='inventory' AND paused_reason='等待广州批次'`，或 `stage='blocked' AND paused_reason='待补可复用的同版本来源模板' AND (source_bundle OR has_template)` 的行进入 batch。没有模板的 blocked 行**不进入 batch**，所以不会占 5 个名额，但也不会被重新检查。
5. `LIMIT 5` 是每 30 分钟最多晋升 5 行；`dispatch_slot` 只防止同一半小时内重复选中同一行。它不是并发上限，也不是搜索或模型预算。
6. `InspectPlanInventory` 把 `inventory` 行按最新盘点算成 `planning`，`gaps` 是缺集数组。
7. `prepareConfiguration` 从 `plan_validated` 领取一集，预留 16000 token，调用 Agent，`SettlePlanDraft`，`RegisterEpisodeConfiguration`；失败时无用量回执、尝试达到 2 或用量为 0 会直接 `blocked`。`configuration.go:27-107`。
8. 研究车道 `RunLane` 每 5 秒轮询：维护、预算等待、草稿、配置、验收观察、研究。媒体车道只做验收与出图。`production.go:19-85`。

**对当前 20 部的直接后果：** 这些作品没有历史 `source_bundle`，也没有旧版 `wiki-episode` 模板；本机已登记的 FX、药屋、罗梅莉亚计划都**没有 `sourceRules`**（`episode_plans` 实测为 NULL），走 `validateLegacySources` 的历史专用分支，不满足 `has_template` 的 `wiki-episode` 条件。配置阶段的 `Next`（`configuration.queries:9-22`）同样只认 `wiki-episode` 或 `source_bundle`，也不会把这些 legacy 计划当成模板。因此每轮领取最多 5 集，前几轮会把这批逐批落到 `blocked/待补可复用的同版本来源模板`；配置阶段即使被领取也会因 `Previous` 为空而 blocked。落完之后没有任何阶段会启动来源发现。

### 1.3 来源与规则现状

- `episode-source-cli.ts` 是人工入口：要求 2–5 条同版本样本，每条必须同时有官方 URL 和独立 URL；调用一次模型生成两条规则，再用全部样本验证，最后人工执行 `episode-source-rule-attach`。
- `validateEpisodeSourceProposal`（`episode-source-task.ts:33-70`）强制“同一对官方/独立站点”，抓取全部样本，只把第一条样本正文交给模型，模型只能返回 `{officialRule,guideRule}`。
- 规则类型只有两种：`json_episode_list`（顶层数组，字段 `episode/title/body`）和 `html_episode_article`（`heading/body` 选择器）。嵌套 JSON 只能走 `episode-plan.ts` 的历史专用分支。
- 规则只存在于单集 `production_policy.source_bundle` 里，没有独立表、没有版本、没有过期、没有跨集复用。
- 双来源硬条件分布在 7 处：
  - `research.go:58-94`：每集恰好 2 份文档，ID 前缀只能是 `official`/`guide`，URL 必须精确等于计划 URL。
  - `research.go:88-137`：每集覆盖度恰好 5 个键（2 份来源 + motive/turn/cause），段落 4–6 条。
  - `episode_plan.go:502-...`：官方 host 和独立 host 各有一份硬编码白名单；`paired` 要求 `guide.Host != official.Host`。
  - `episode_configuration.go:64`：登记时要求 `spec.SourceNumber` 等于模板声明的值，bundle 未声明时为零，即 paired 路径只允许 bundle 带来的季偏移。
  - `episode_capture.go:47`、`episode_plan.go:404`：外部采集导入和验收再次调用 `validateSourceDocuments`，缺一份即失败。
  - `episode_source_bundle.go:40-45`：附接要求 `rules.Guide='paired'`、2–5 个样本、官方和独立两份 proof。
  - TS 侧：`episode-source-task.ts:38-45` 要求 2–5 条且同一对 host；`episode-plan.ts:52-63` 的 paired 分支要求两份文档并执行 `checkIndependentSources`；`episode-configuration-task.ts:15-16` 要求 `sourceRules.guide === 'paired'`。
- 除“文档数”外，还有三个隐含假设：
  - `episodeSpec.validate()`（`episode_plan.go:68-104`）要求 `GuideTitle` 非空、4–6 个剧情节点，且至少一处 `officialSentence`。
  - `episodeOutline`（`episode-plan.ts:255-257`）直接 `docs.find(d => d.id === 'guide-' + p.number)!`；B 级只有官方文档时会崩溃。
  - `RegisterEpisodeConfiguration` 用 `guide` 句子的顺序定位每个 beat（`episode_configuration.go` 中 `starts` 循环）；B 级需要改用官方句子。

### P2：可观测与容量问题

- `LIMIT 5` 只是晋升速率，没有显式并发上限；如果多个批次重叠，实际在飞任务数不受控。当前 systemd 单实例 + `dispatch_slot` 已基本避免重叠， MVP 不加新限制。

## 4. 目标架构

```
                    ┌──────────────────────────────┐
                    │ PostgreSQL（唯一事实源）      │
                    │ origins / rules / tasks /     │
                    │ requests / captures /         │
                    │ acceptances / release pointers│
                    └──────────────▲───────────────┘
                                   │
制作请求 ──► 来源任务 tick ──► agent loop（发现/规则/抓取）──► generate-and-filter ──► 快照/证据
 (广州队列)   (入队/claim)      (只读工具 + 上下文预算)         (固定验证器)          (evidence)
                                   │
                                   ▼
                        复用现有 AttachSourceBundle
                                   │
                                   ▼
                    请求回到 inventory / 等待广州批次
                                   │
                                   ▼
                现有 5/30min 领取 ──► 配置 ──► 五维验收 ──► 读者发布（不变）
```

关键边界：

- **两层控制面。** 来源任务内部由模型驱动只读工具循环；`stage`、租约、预算、`verified`、附接和发布只由 Go 写。模型不能写库、不能触发发布、不能执行任意 JavaScript（见 0.2）。
- **来源任务先于生产晋升。** 来源任务在请求仍 `blocked` 时运行，使用独立的抓取/模型预算，不占 5 集/30 分钟的生产额度。
- **来源失败不是制作失败。** 来源任务有独立状态；一集来源失败只阻塞该集，不阻塞同作品其他集，也不把整部作品标成制作失败。
- **验证通过后复用现有附接路径。** 来源 tick 把 bundle 写回请求（`production_policy.source_bundle`），请求回到 `inventory/等待广州批次`；下一轮 dispatch 照常按 5 集上限晋升。**不需要改 dispatch SQL**，这是本方案的最小改动。
- **B 级不降低验收标准。** B 只改变“需要几份来源文档”和“写作时用哪份叙述句”；五维检查、图片检查、发布门槛不变。
- **C 级永不自动通过。** 可以继续在预算内找来源，但预算耗尽后停在 `blocked/weak_source`，等待运维提供新来源或显式放弃，不默认进入人工复核队列。
- **已发布章节只读。** 新链路只写 `publishToReader:false` 的本地计划；发布器与已发布锚点不改。

## 5. Source Evidence Model（A/B/C）

### 5.1 标准身份与来源身份必须分开

- `world_slug` 已经唯一标识“作品 + 发行版本”（例如 `apothecary-diaries-s3-2026`），不需要再引入 `edition_id`。任务唯一键用 `(world_slug, number)`，并用 `request_id` 绑定对应的单集制作请求。
- `number` 永远是系统标准集号；`source_number` 是来源页集号，允许偏移。任何来源集号**不得覆盖** `number`。
- 文档 ID 统一用 `official-<number>` / `guide-<number>`；`locator` 里写来源集号。这个约定现有 `sourceDocument` 已经在用（`episode-plan.ts:155-158`），继续保留。
- 季/系列总话数只作为证据字段（`season`、`source_total`、`source_offset`），不进入主键。

### 5.3 等级定义

| 等级 | 来源构成 | 自动通过 | 文档数 | 覆盖度键 | 段落数 |
| --- | --- | --- | --- | --- | --- |
| A | 官方 + 独立，身份一致，独立来源非转载 | 是 | 2 | 5（2 来源 + 3 类引用） | 4–6 |
| B | 单一可靠官方来源，全部 B 条件成立 | 是 | 1 | 4（1 来源 + 3 类引用） | 4–6 |
| C | 搜索摘要、不可核转载、残缺聚合、社媒、季/集号歧义 | 否 | — | — | — |

注意：**A 级要求“独立来源不是转载”；转载只让该独立来源失去 A 资格，不自动把整个任务降为 C。** 如果官方来源仍满足全部 B 条件，任务可以按 B 自动通过，并在 `decision.reasons` 记录“独立来源疑似转载，按 B 处理”。这与“单一可靠官方来源允许自动通过”一致。

### 5.4 官方归属与域名确认

B 级不能因为“只有一个 URL”就被判低质量；但必须证明这个 URL 是**该作品该版本的官方来源**。

新增 `episode_source_origins`（每部作品一行或数行）：

| 字段 | 用途 |
| --- | --- |
| `world_slug` | 作品 + 版本 |
| `host` | 官方域或官方发行平台域 |
| `role` | `official` / `official_distributor` |
| `evidence_url` | 证明归属的官方页面（作品介绍、发行公告、版权页） |
| `episode_list_url` | 官方分集索引页，可空 |
| `url_pattern` | 只允许 `{n}` / `{n:02}` 的 URL 模板，可空 |
| `cdn_hosts` | 允许的 CDN/静态域名数组，可空 |
| `work_marker` | HTML 页面必须出现的作品标识（标题或固定串），可空 |
| `source_offset` | 来源集号 = 标准集号 + offset |
| `source_total` | 来源季总集数 |
| `status` | `active` / `paused` / `retired` |

判定规则：

1. **官方域**：`host` 来自 `evidence_url` 的最终主机；必须是 HTTPS、无凭据、无自定义端口。`evidence_url` 页面必须能识别作品和发行版本（标题、版权方、放送季）。
2. **官方 CDN / 第三方分发**：允许两类：
   - `role='official'` 的官方站及其 `cdn_hosts`；
   - `role='official_distributor'` 的官方发行平台（例如 animatetimes、animestore、b-ch）。必须登记 `evidence_url`，证明该平台是这个作品/版本的官方发行或官方新闻渠道。
   - 聚合站、搬运站、用户 wiki、未登记的社媒账号不在 `official_distributor` 内，只能作为独立来源候选（且仍受 6-gram 转载检测）。
3. **重定向与 canonical**：
   - 发现/验证阶段使用单独的 `fetchSourcePage`（允许重定向并记录完整跳转链和 `finalUrl`）；现有 `fetchSourceText` 保持 `redirect:'error'`，用于执行阶段。
   - 若 `finalUrl` 的主机不在 `host + cdn_hosts`，判 C，不自动通过。
   - 解析 `<link rel="canonical">`：canonical 指向 `host` 或 `cdn_hosts` 时记录为别名；指向外部时判 C。
   - 执行阶段用 `finalUrl` 抓取，仍保持 `redirect:'error'`，确保规则绑定的是最终地址。
4. **JSON API / 嵌套 JSON / HTML / 合集页**：
   - JSON 顶层数组：`json_episode_list`。
   - 嵌套 JSON：规则增加受限路径语法（第 7.3 节），不允许任意 JavaScript、不允许 `eval`、不允许 jq 表达式。
   - HTML 单集：`html_episode_article`，选择器必须是 CSS，正文容器必须有唯一 article/main/body 祖先。
   - 合集页（一个页面含多集）：JSON 数组一次抓取；HTML 索引页只用于发现候选 URL，不作为正文来源；正文仍使用单集页或 JSON 记录。
   - 社媒/官方账号：只有登记为 `official_distributor` 且 `evidence_url` 能证明归属时才按官方处理；普通社媒帖子按 C。
5. **作品/版本识别**：
   - HTML：`work_marker` 必须出现在页面正文或标题中；页面标题、版权方、放送季不得与作品版本冲突。
   - JSON：端点必须是该作品登记过的官方端点；若返回多条作品/季，必须用 `filter` 精确定位。
6. **集号/季号/特别篇**：
   - 目标页集号必须唯一命中 `source_number`；
   - `source_number = number + source_offset`，offset 必须由 `offsetProof` 证明（相邻集标题、季总集数、系列总话数）；
   - 不得用“页面看起来像”推断季号；无法证明时停在 `blocked/identity`。
   - 特别篇/回顾/OVA 不得按集号偏移映射进 TV 正片。盘点只把 TV 正片集号作为 `missing`；若作品确需特别篇，必须登记独立 canonical 标识（`kind=special`），不参与 TV 集号连续性和相邻集验证，默认按 C 处理，不自动通过。
7. **标题**：
   - 标准标题来自盘点快照新增的 `episodeTitles`，每项含 Bangumi 的 `name` 与 `name_cn`；也可以用运维一次性写入的 `canonical_title`。
   - A 级比较两份来源的标题：规范化后相等即可，不要求外部标准标题。
   - B 级自动通过要求标准标题非空；目标页标题规范化后等于 `name`、`name_cn` 或运维写入的标题，且不等于相邻集标题。这样可以避开日文原名与中文页标题字面不一致造成的假阴性。
   - 没有标准标题时 B 不自动通过。任务可以先找第二条来源走 A；两条都找不到才停 `blocked/identity`。不把缺标题变成人工复核默认流程。

### 5.5 单来源内容完整性

B 级仍要求：

- 正文 ≥ 60 字（沿用现有下限），≤ 6000 字；
- 句子可定位，`Sentences` 非空且每句能在正文中找到（沿用 `validateSourceDocuments`）；
- 不是模板占位页：正文不得只有标题、不得包含“敬请期待 / Coming soon / TBA / 未定”等占位串；
- 页面快照 `pageSha256` 与 `textSha256` 齐全，抓取时间在 24 小时内；
- 相邻集至少 1 集（优先 `n-1`；若 `n+1` 已播出则两者都用）能通过同一规则提取，且标题/正文不同；
- 错集号负例（`number=0x7fffffff`）和错标题负例必须失败（沿用 `checkEpisodeSourceRule`）；
- 季过滤/偏移必须有证明。

**最新一集没有 `n+1` 不阻塞。** B 只要求“至少一个相邻集”；如果目标是最新播出集，`n-1` 足够。若连 `n-1` 都没有（例如第 1 集且没有第 2 集），B 不能自动通过，停在 `blocked/identity`。

### 5.6 自动通过判定矩阵

| 条件 | A | B | C |
| --- | --- | --- | --- |
| 官方来源存在且 origin 已登记 | 必须 | 必须 | 可有 |
| 独立来源存在且 host 不同 | 必须 | 不需要 | 可有但不可信 |
| 独立来源 6-gram 重合 < 0.8 | 必须 | — | — |
| 作品/版本/季/集号可证明 | 必须 | 必须 | 必须，否则 C |
| 标准标题非空且目标页匹配 | 不需要，用两来源相等代替 | 必须 | 不适用 |
| 两来源标题规范化后相等 | 必须 | — | — |
| 相邻集至少 1 集通过 | 必须 | 必须 | 不适用 |
| 错集号/错标题负例 | 必须 | 必须 | 不适用 |
| 正文完整、非占位 | 必须 | 必须 | 不适用 |
| 快照 ≤ 24h | 必须 | 必须 | — |
| 规则 `verified`，本次目标页与相邻集复验通过 | 必须 | 必须 | — |
| 自动通过 | 是 | 是 | 否 |

### 5.7 永不自动通过

- 作品/版本/季无法确认，或集号/偏移需要猜测。
- 官方 origin 未登记，或归属证据无法证明。
- 目标页只有目标集，没有相邻集可验证。
- 错集号或错标题负例仍然命中。
- 正文 < 60 字、模板占位、只有标题没有正文。
- 独立来源与官方 6-gram 重合 ≥ 0.8（该独立来源失去 A 资格；若官方不满足 B 条件，则整体 C）。
- 规则复验失败，且本任务也生成不出可验证的替代规则。
- 快照超过 24 小时。
- 只有 C 级候选，或抓取/模型预算耗尽。

C 级可以继续找来源，但每次抓取计入 `fetch_calls`；预算耗尽后停在 `blocked/weak_source`，不通过增加重试、放宽阈值或人工改等级来绕过。

### 5.8 与现有五维的衔接

- A：`validateSourceDocuments` 保持每集 2 份；覆盖度 5 键；段落 4–6。
- B：文档数改为 1；覆盖度 4 键；段落仍 4–6（因为 `episodeSpec.validate` 要求 4–6 个节点，验收要求 `len(claims)==len(beats)`）。**不是 3 段。** 写作链通过统一的叙述来源别名取句子，见 8.2。
- C：不进入 `RegisterEpisodeConfiguration`；没有计划、没有验收、没有发布。
- 人物、剧情、世界观、时间线、图片五维检查、`scope_acceptances`、`scope_heads`、发布器均不改。

## 6. 来源任务状态机与 agent loop

`discovering`、`rule`、`capturing` 内部是 agent loop：模型观察当前候选和验证结果，调用只读工具，决定下一步，直到找到候选、规则通过或预算耗尽。`stage` 仍由 Go 在固定验证结果上推进。模型不能直接改状态。

### 6.1 状态

```
queued ──claim──► discovering ──► rule ──► capturing ──► verified ──► done
  ▲                   │             │            │
  │                   ▼             ▼            ▼
  └──────────────── blocked ◄───────┴────────────┘
  │
  └── origin/规则更新、运维重试 ──► queued

任何活动态：租约过期 → queued
任何状态：运维停止 / 不可重试 → closed
```

说明：

- `queued`：待领取。`next_attempt_at` 控制退避；失败重试回到这里，不另设 `retry_wait`。
- `discovering`：找候选。模型用 `search_candidates`、`fetch_page`、`read_inventory` 观察官方 origin、相邻 URL、JSON 端点。
- `rule`：规则命中或生成，并完成固定程序验证。生成走 generate-and-filter，模型调 `check_rule`；命中已验证规则时 `model_calls=0`。
- `capturing`：抓目标页。模型用 `fetch_page`、`parse_json` 返回原文和解析结果；Go 保存证据与 SHA。任务 `evidence` 是来源快照证明；计划生成后现有采集阶段仍写 `episode_source_captures`，MVP 不改该表。
- `verified`：证据成立、附接完成前的中间态。同一 tick 内附接 bundle 后转 `done`。
- `done`：附接成功，或来源任务完成但请求已被后续流程处理。终态。
- `blocked`：自动重试耗尽的阻塞，`next_attempt_at` 置空，避免无限重试。`reason` 区分 `no_candidate` / `weak_source` / `identity` / `budget` / `conflict`。只有 origin/规则更新或运维 `episode-source-retry` 才回到 `queued`。
- `closed`：终止。`reason` 区分 `cancelled`（运维停止）、`fatal`（规则 schema/安全违规）、`superseded`（请求已晋升或发布，无需附接）。
- `steps` 列按阶段记录 `{status, attempts, error, at}`。单个 `stage` 之外仍能看到发现、规则、抓取各自的最后结果。

### 6.2 迁移表

| 当前 | 事件 | 守卫 | 下一状态 | 副作用 |
| --- | --- | --- | --- | --- |
| queued | 领取 | 租约空闲、`next_attempt_at <= now()` | discovering | 写 `lease_owner/lease_until`，`attempts+1` |
| discovering | 找到候选 | origin 已登记、URL 在允许域 | rule | 写 `candidates`、`steps.discovery` |
| discovering | 无候选 | 抓取预算未耗尽、attempts<2 | queued | 退避，`fetch_calls+1` |
| discovering | 无候选 | 预算耗尽/attempts=2 | blocked | `reason=no_candidate` |
| rule | 命中已验证规则 | 目标页与相邻集复验通过 | capturing | 写 `rule_id`，`model_calls` 不变 |
| rule | 无命中 | 模型预算可用 | capturing | 调模型生成并验证，`model_calls+1` |
| rule | 规则验证失败 | attempts<2 | queued | 记录失败，退避 |
| rule | 规则验证失败 | attempts=2 | blocked | `reason=identity` |
| capturing | 证据保存 | SHA/完整性/新鲜度通过 | verified | 写 `evidence` |
| capturing | 抓取或校验失败 | attempts<3 | queued | 退避，`fetch_calls+1` |
| capturing | 抓取或校验失败 | attempts=3 | blocked | `reason=weak_source` |
| verified | 附接成功 | 请求仍为 inventory/blocked、`reserved=0` | done | 写回 `source_bundle`，请求保持“等待广州批次” |
| verified | 请求已晋升或发布 | — | closed | `reason=superseded`，不写请求 |
| verified | 附接写库失败 | 请求仍符合附接条件 | verified | 下一 tick 重试附接，保留 evidence |
| 任意活动态 | 租约过期 | — | queued | 回收租约，`next_attempt_at=now()+1m`，保留证据 |
| blocked | origin/规则更新或运维重试 | — | queued | 清 `reason`，保留证据，重新计算退避 |
| 任意 | 运维停止 | — | closed | `reason=cancelled`，保留证据 |
| 任意 | 规则 schema/安全违规 | — | closed | `reason=fatal`，保留证据 |

### 6.3 与生产请求的关系

- 任务由制作请求生成：`request_id NOT NULL`，唯一键 `request_id` 与 `(world_slug, number)` 同时成立。任务不创建请求。
- Agent 工具集全部只读：`search_candidates`、`fetch_page`、`parse_json`、`check_rule`、`read_inventory`。没有写库、附接或发布工具，这些动作只由 Go 在固定验证结果上执行。
- 每次来源 tick 先跑 `EnqueueTasks`：筛 `episode_production_requests` 中 `production_policy->>'queue'='gz-20-aired-20261125'`、`first_episode=last_episode`、stage 为 `inventory` 或 `blocked`、`paused_reason` 为 `等待广州批次` 或 `待补可复用的同版本来源模板`、且没有 `source_bundle` 的行，插入任务并 `ON CONFLICT DO NOTHING`。124 条请求在第一次 tick 生成 124 个任务，之后不重复。`missing_usage_receipt` 等制作侧阻塞不会生成来源任务。
- tick 顺序是 `EnqueueTasks` → `AttachVerified`（重试上一轮未附接的 verified）→ 领取 1 条来源任务。
- 抓取、模型生成、规则验证、取证分别由 `fetch_calls`、`model_calls`、`episode_source_rules.status/proofs`、`evidence`、`steps` 记录，互不覆盖。模型输出永远不直接等于 `verified`。
- tick 每次只领 1 条，不按作品加锁；不同作品的任务按 `created_at` 轮转，多个作品、多个集数在同一 lane 串行推进，一个来源失败不拖住其他集。
- `verified` 后附接只在请求仍为 `inventory` 或 `blocked` 且 `reserved=0` 时执行。现有 `AttachSourceBundle` 把 `source_bundle` 写回请求，并保持 `等待广州批次`；下一轮 dispatch 才消耗 5 集名额。
- 现有附接 SQL 写死 `paused_reason='等待广州批次'`，只适用于广州队列，也只匹配 `first_episode=last_episode` 的单集请求。MVP 不 seed 其他队列；其他队列要先给附接 SQL 加参数。
- 请求已有不同的 `source_bundle` 时先比对；不同则转 `blocked`，`reason=conflict`，不覆盖已核对来源。
- 请求在来源运行中被晋升或发布，任务转 `closed/superseded`，不写请求。
- 来源任务失败不修改请求 `stage`；请求仍停在 `blocked`，`paused_reason` 区分“来源未就绪”和“制作失败”。新增 `来源未就绪：<reason>` 时不覆盖原“待补模板”。该文案不会被 dispatch 重新检查，来源 tick 会在 origin/规则更新后重试，所以不需要改 dispatch。

## 7. 来源规则 Registry 数据模型

### 7.1 为什么不复用 `episode_plans.spec`

现有规则存在单集 `production_policy.source_bundle` 中：无法按站点查询、无法跨集复用、无法记录过期、无法统计命中率。放进 `episode_plans.spec` 只是把问题搬到另一张表。

### 7.2 绑定粒度比较

| 方案 | 复用范围 | 问题 |
| --- | --- | --- |
| 按作品 | 同作品所有集 | 换站点就失效，无法跨作品 |
| 按站点 | 同站所有作品 | 选择器可能因栏目不同而失效 |
| **按站点 + 页面类型** | 同站同栏目 | **推荐**；规则体可复用，身份校验兜底 |
| 按集 | 单集 | 等于没有复用 |

推荐：规则体按 `site_host + page_type` 复用；作品/版本/季/集号偏移作为任务绑定，不写进规则体。这样 FX 久留美的规则可复用到同站其他作品，但每集仍用相邻集和负例验证身份。

### 7.3 规则语法（受限，不允许任意 JavaScript）

现有两种规则保留并扩展：

```jsonc
// JSON 分集列表（顶层数组或受限路径）
{
  "kind": "json_episode_list",
  "rowsPath": "",              // 空=顶层数组；否则是点路径，如 "data.list"
  "episode": "acf.index",      // 点路径；值必须能解析成整数
  "title": "acf.title",
  "body": "acf.story",
  "filter": { "field": "acf.season_id", "equals": "season1" } // 可选
}

// HTML 单集
{
  "kind": "html_episode_article",
  "heading": "article h1",     // 必须唯一命中且含集号与标题
  "body": "article .story p"
}
```

约束：

- 路径只允许“键名 + 点”，不允许通配符、函数、表达式、`eval`、`Function`、jq。
- `filter` 只支持单字段等值；需要多条件时增加 `all` 数组，仍为声明式。
- `heading`/`body` 只允许 CSS 选择器；`body` 节点必须与 `heading` 同属一个 `article/main/body` 容器。
- 字段长度上限沿用现有 256；正文 60–6000 字。
- 规则 SHA 用规范化 JSON 计算；同一规则重复写入不新增行。
- 模型只返回规则对象；`parseEpisodeSourceRule` + 固定程序验证决定是否 `verified`。

### 7.4 表一：`episode_source_origins`

见 5.4。主键 `(world_slug, host)`；索引 `(host)`。20 部作品一次性由运维登记；`evidence_url` 必须可复查。

### 7.7 失效与复用

- 规则没有到期计时器。每次使用都复验目标页、相邻集和负例；失败当场暴露，不静默复用。
- 任务进入 `rule` 时按 `(site_host, page_type)` 查 `verified` 规则，`scope_world` 相同的排前，`verified_at` 新的排前。最多试 2 条；都不通过才调用模型生成。
- 新规则写新行，旧行保留；`version` 递增。相同 `rule_sha256` 不重复插入。
- 站点改版靠“复验失败率”发现，不靠 90 天巡检。连续失败不自动降级规则，避免一集异常误伤同站其他作品。
- `deprecated` 只能由运维显式设置，保留用于解释历史任务；不删除。

### 8.3 验收与缺口文案

- `AcceptPlannedEpisodes` 的 `gap` 文案“等待同集、双来源的取证校对”改为按 mode 生成（A/B）；这是界面文案，不改验收逻辑。
- `valid` 仍要求 `validateSourceDocuments`、`validateEpisodeClaims`、`len(claims)==len(beats)` 全部通过；B 不降低五维。
- 图片维度保持不变；B 不跳过三张候选、选图、裁切和摘要。

### 8.4 不允许的“简化”

- 不能因为 B 级就把五维降为三维。
- 不能因为来源少就跳过图片验收。
- 不能把 C 级默认送人工复核；默认是停在阻塞状态，人工只在需要时介入。
- 不能修改已发布章节、已冻结段落锚点或已入选图片摘要。
- 不能让模型输出直接标 `verified`；状态只能由固定程序验证后由 Go 服务写入。

## 9. 租约、幂等、重试与恢复

### 9.1 租约

- 来源任务按活动阶段领取，租约 10 分钟；`lease_owner + lease_until`。
- 领取 SQL 用 `FOR UPDATE SKIP LOCKED LIMIT 1`，一次只领 1 条；一集失败不影响其他集。
- 过期租约由同一 tick 回收：`stage in ('discovering','rule','capturing') AND lease_until < now()` → `queued`，`next_attempt_at=now()+1m`。来源任务没有预留字段，不需要释放；保留 `evidence/candidates/steps`。
- 不使用全局锁；需要串行化的只有单任务行锁和预算的短事务。全部用 PostgreSQL 原子事务与现有 Go 调度，不引入 Redis、Kafka 或新消息中间件。

### 9.2 幂等键

- 任务唯一键 `(world_slug, number)` 与 `request_id`。
- Agent 调用 ID（同时是 Pi run ID）：`<world>:<number>:<stage>`，稳定，重试复用。回执 subject 是 `source:` 加这个 ID，即 `source:<world>:<number>:<stage>`，不会出现双重前缀。规则变化时在 ID 末尾加 `:<ruleSha256>`。
- 规则写入：`rule_sha256` 唯一；相同规则重复附接不新增行。
- 证据/快照写入：`(task_id, rule_sha256, pageSha256)` 去重；重复导入不重复计费。
- 生产请求：现有 `episode_configuration_attempts` 单活跃索引继续使用。

### 9.3 重试策略

| 阶段 | 最大尝试 | 退避 | 不可重试 |
| --- | --- | --- | --- |
| 候选/抓取 | 2 | 1m / 5m | 预算耗尽、无官方 origin |
| 规则生成/验证 | 2 | 5m | 身份歧义、负例命中 |
| 快照/证据 | 3 | 1m / 5m / 15m | SHA 不符、正文过短、占位页 |
| 配置生成 | 2 | 现有 5 分钟租约 | 已登记、计划锁冲突 |

达到上限 → `blocked`，记录 `last_error`，不自动升级为人工复核。

### 9.4 配置崩溃恢复（P1-6 的具体修法）

现状：`Expire` 把超时 attempt 标记为 `配置执行超时，需对账`，并把请求置 `blocked/missing_usage_receipt`；`Next` 只选 `stage='plan_validated' AND paused_reason IS NULL`，所以该请求永远不会再被领取。同时，`episode_call_reservations` 的预留没有被结算，`request.reserved` 仍占着 16000，直接重试会因剩余额度不足而再次失败。

最小修法（保留同一 call ID 和同一预留）：

1. `Expire` 对每条超时 attempt（call ID）分别处理：
   - 若 `episode_call_reservations` 已结算：结束 attempt；请求置回 `plan_validated`，允许重试。
   - 若未结算且 `model_usage_receipts` 已有该 call 的回执：调用 `settle_episode_call(request, call, tokens)`，扣减 `consumed`、释放 `reserved`；结束 attempt；请求置回 `plan_validated`。
   - 若未结算且没有回执：**保留预留**，结束 attempt 并记录 `error='配置执行超时，需对账'`；请求置回 `plan_validated`、`paused_reason=NULL`，等待同一 call ID 重试。
2. `Next` 增加“复用最近一次超时 attempt 的 call ID”：
   - 查最近一条 `error='配置执行超时，需对账' AND finished_at > now()-1h` 的 `id`；
   - 若存在，把该 attempt 行重新打开（`finished_at=NULL, error=NULL`），跳过 `Start`，也不再 `Reserve`（预留仍在），直接用同一 call ID 调 Agent；Pi 恢复同一 durable session，不产生新模型调用；
   - 若不存在，按现有逻辑生成新 call ID 并预留。
3. 重试后仍无用量回执：
   - 若 `attempts<2`，用新增的 `release_episode_call(request, call)` 释放剩余预留（`reserved=reserved-ceiling`、`settled_at=now()`、记录 `reconcile_released`），请求回到 `plan_validated`；
   - 若 `attempts=2`，释放预留并置 `blocked/missing_usage_receipt`，不再自动重试。
4. 对账任务（每 15 分钟）：
   - 比较 `episode_source_tasks.model_used` 与 `model_usage_receipts` 中 `subject like 'source:%'` 的汇总；
   - 比较配置 attempt 的 `actual` 与 receipt；
   - 未结算预留超过 1 小时 → 释放并记录 `reconcile_released`；
   - 只调整状态和用量，不删除任何证据。

这样既避免“Pi 完成但 PG 未写入”重复调用模型，也避免预留泄漏导致请求永久 `insufficient_remaining_tokens`。

### 9.5 来源任务的 Pi 对账

- Agent 入口返回 `{tokens, rule?, documents?, proofs?, error?}`；Go 在同一事务里写 task/evidence/attach。
- 若 Go 在 HTTP 返回后崩溃：租约过期，任务回 `queued`；下一次用同一 call ID 调 Agent，Pi 返回已完成结果，不再调用模型。
- 若 Agent 在模型调用中崩溃：Pi resume 同一 session；若仍失败，记录 `model_calls`，任务回 `queued` 并退避。
- 若 Pi 完成但 PG 未写入：用同一 call ID 重新调用 Agent，Pi 返回已完成结果后写 task 和 evidence；receipt 只结算一次。

## 10. 三类预算与对账

### 10.1 生产批次预算

- 保持每 30 分钟最多晋升 5 集，`dispatch_slot` 不变。
- 它是**晋升速率**，不是并发上限，也不是来源预算。
- 来源任务在晋升前运行，不占这 5 个名额；来源验证通过后的附接也不占；只有下一轮 dispatch 的晋升占 1 个名额。
- 可选增强（不进 MVP）：按 `stage in ('inventory','executing')` 计数“每车道在飞上限 5”，不需要新表。

### 10.2 抓取/搜索预算

本方案 **MVP 不接外部搜索 API**。广州出口受限，且搜索 API 会引入新依赖、密钥和不可控成本。候选来源来自：

1. 同作品更早集的官方/独立 URL（已登记计划）；
2. `episode_source_origins.episode_list_url` 或 `url_pattern`；
3. JSON 端点本身（一次抓取得到全季）；
4. 运维一次性提供的 2–5 条样本 URL（沿用现有 CLI 输入）。

计数位置：

| 维度 | 建议值 | 计数 |
| --- | --- | --- |
| 每任务抓取/HEAD | 8 | `fetch_calls`；最坏情况是试 2 条规则（各 2 页）加采集目标与相邻集（2 页），留 2 次重试 |
| 每作品每日任务 | 10 | 按 `world_slug` 聚合 |
| 每 tick 领取 | 1 | 领取 SQL |
| 候选 HEAD/GET | 计入抓取 | 同上 |

预算耗尽 → `blocked/no_candidate` 或 `blocked/weak_source`，不影响生产请求，不影响其他集。

### 10.3 模型预算

- 科目：`source:<call>`；`call` 是任务的当次 Agent 调用 ID，与生产请求的 60000 token 分开。
- 每任务上限 8000 token；每日全局上限 100000（可配置）。
- **不做预留。** 单 lane 每 tick 只领 1 条，同一任务不会并发调用：
  - 调用前：在同一事务检查 `model_used < 8000`；日上限按 `model_usage_receipts` 当天 `subject like 'source:%'` 汇总，用 `pg_advisory_xact_lock(hashtext('source-budget:'||current_date))` 串行化检查，不新增预算表。
  - 调用后：`model_used = model_used + tokens`，按回执结算。
  - 崩溃：计数保留；对账按 receipt 修正，重复回执只算一次。
- Agent 侧只改一处：`runProductionModel` 对 `source_rule` 使用 `contentProvider(id, stage, 'source', true)`，让 `model_usage_receipts.subject` 变成 `source:<call>`；`budgetDispatch` 仍不识别 `source:`，返回 noop，不影响现有生产预算。这样规则生成成本可按 subject 对账，但不需要改预算协议。
- 超限 → `blocked/budget`，不把生产请求标失败。
- 生产请求的 `consumed` 不得包含 `source:` 科目；若发现混入，修正 subject 映射。

### 10.4 对账

每日一次：

1. `episode_source_tasks.model_used` 汇总 vs `model_usage_receipts` 中 `subject like 'source:%'` 的汇总。
2. 差值 > 1% 或 > 1000 token → 告警。
3. 生产请求 `consumed` 不应包含 `source:`；若混入则修正。
4. 重复回执按 receipt id 去重；不重复扣减。
5. 配置 attempt 的预留未结算超过 1 小时 → 按 9.4 释放并记录 `reconcile_released`。来源任务没有预留，不参与这一项。

### 10.5 用户问题的直接回答

| 问题 | 答案 |
| --- | --- |
| 5 集额度在哪一步扣除 | 只在 `dispatch-aired-episodes.sql` 的晋升 UPDATE；来源任务、附接都不扣 |
| 来源发现是否占用 5 集 | 不占 |
| 已有规则复用是否占用额度 | 不占生产额度；只计抓取次数 |
| 搜索失败是否占用生产额度 | 不占 |
| 模型调用失败如何处理 | 来源任务回 `queued` 退避，或转 `blocked`；生产请求不变 |
| 租约过期如何恢复 | 回收为 `queued`，按 `next_attempt_at` 退避，保留证据；来源任务没有预留可释放 |
| Agent 中途重启如何恢复 | 同一 call ID 让 Pi resume |
| 重复领取如何避免 | `FOR UPDATE SKIP LOCKED` + 单活跃租约 + 唯一键 |
| Pi 完成但 PG 未写入如何对账 | 同一 call ID 重调 Agent 取回结果；receipt 只结算一次 |

| 3 季偏移 | 药屋少女的呢喃 | 54/55 → 第 3 季 6/7；允许 `SourceNumber != 0` | 偏移证明成立，配置登记成功，五维通过 |

每阶段门禁：

- 已发布章节哈希、段落锚点、入选图片摘要不变。

- 没有新增 `blocked/missing_usage_receipt`。
- `episode_source_tasks` 总数不随 tick 增加；已附接请求不重复生成任务。
- 任何阶段都可以停来源 tick；请求回到 `blocked/待补模板` 或继续等待，不影响已晋升任务。

**不能因为新来源系统上线而重建已经登记的制作任务。** 阶段 1 只新增 tasks/origins/rules；附接只改 `production_policy` 和 `stage` 的两个已知字段，不改请求 ID、集号、预算和已登记计划。

## 15. 可观测性指标

### 15.1 任务与来源

- `episode_source_tasks` 按 `stage`、`evidence_level`、`reason` 的计数。
- 官方来源发现率 = 找到 origin 的任务 / 总任务。
- 规则命中率 = `rule_id` 非空且本次复验通过 / 进入 `rule` 的任务。
- 规则复用率 = `model_calls=0` 且 `rule_id` 非空的任务 / 进入 `rule` 的任务。
- A/B/C 分布；B 自动通过率；C 占比。
- 相邻集验证通过率、负例失败率、6-gram 重合分布。
- 每阶段耗时 p50/p95；租约过期次数；重试次数。
- 单集来源成本、每部作品日成本、`source:` 科目用量。

### 15.2 生产与验收

- 队列按 `stage`、`paused_reason` 的计数；晋升速率；在飞任务数。
- 五维验收通过率、各维度缺项数。
- 配置失败原因、`missing_usage_receipt` 数量。
- 发布尝试次数、发布失败原因（应保持 0 变更）。

### 15.3 建议视图

```sql
CREATE VIEW episode_source_queue AS
SELECT world_slug, stage, evidence_level, reason, count(*) AS tasks,
       min(created_at) AS oldest, sum(model_used) AS tokens
FROM episode_source_tasks
GROUP BY 1,2,3,4;

CREATE VIEW episode_source_daily AS
SELECT date_trunc('day', created_at AT TIME ZONE 'Asia/Shanghai') AS day,
       evidence_level, stage, count(*) AS tasks
FROM episode_source_tasks
GROUP BY 1,2,3;
-- 每日 token 成本从 model_usage_receipts 的 source: 科目汇总，不从本视图取。
```

告警：

- 任务在 `discovering`/`rule`/`capturing` 超过 30 分钟。
- 同一任务租约过期 ≥ 3 次。
- 日模型预算达到 80%。
- 官方来源发现率连续 3 天低于 50%。
- 自动通过后五维验收失败率 > 5%。
- 对账差值 > 1%。

工作台接入可以后续再加 `/stats/source-pipeline`；MVP 先用 SQL 视图和现有 heartbeat，不扩前端。

## 16. 回滚方案

| 触发 | 动作 | 影响 |
| --- | --- | --- |
| 新链路异常 | 停来源 tick（systemd 或环境开关），不附接新任务 | 现有模板路径继续；新任务停在原地，不写计划 |
| 附接后请求异常 | 把请求置回 `blocked/待补模板`，保留 `source_bundle` 供排查 | 不发布、不改已发布章节 |
| B 级验收误判 | 停 B 模式；已有 B 计划不改，人工复核 | 不发布、不改已发布章节 |
| 规则错误 | 规则置 `deprecated`；任务回 `rule` 或人工附接 | 不删除历史证据 |
| Agent/OpenAI 故障 | 任务回 `queued` 并退避；生产队列不受影响 | 旧模板继续跑 |
| 迁移问题 | 代码回滚；新表保留不读 | 不 drop，不丢数据 |
| 预算异常 | 停来源模型调用，保留 `model_used` 计数供对账 | 规则生成暂停，生产继续 |

回滚顺序：

1. 停来源 tick（`systemctl stop` 或环境开关），保留 worker。
2. 把 `discovering/rule/capturing` 的任务标 `closed`，`reason=cancelled`，保留证据。
3. 已附接但未晋升的请求置回 `blocked/待补可复用的同版本来源模板`；已晋升的请求交给现有流程。
4. 如需回退迁移，先导出任务证据，再 drop；否则保留。
5. 验证生产队列 `stage` 分布与回滚前一致，发布尝试为 0。

## 17. 最小可落地 MVP

### 17.1 范围

1. **迁移 068**：`episode_source_origins`、`episode_source_rules`、`episode_source_tasks`；不改已有表。任务表用 `request_id` 绑定单集请求，不建过期列和预留列。
2. **Go 来源服务**：`episode_source.go` + `source.queries`，实现 `EnqueueTasks`、claim、lease、候选、规则绑定、预算、证据、附接；只保留 `episode-source-retry`、`episode-source-status` 命令。
3. **调度**：研究车道每 60 秒跑一次来源 tick；先跑入队 SQL，再领 1 条；来源 tick 不阻塞现有 draft/configuration/research。
4. **Agent**：`episode-source-task.ts` 支持单官方样本和可选的第二来源、1–5 样本、相邻集、目标无标题、偏移；模型不返回等级或模式；`episode-source-rules.ts` 支持受限 JSON 路径和 season filter；`server.ts` 新增 `/internal/source/<task>`。
5. **验收**：7 个校验点按 mode 动态；B 级 1 份文档、4 键覆盖、4–6 段；`episodeOutline`/配置 `starts`/research 提示词支持官方-only。
6. **附接**：扩展 `AttachEpisodeSourceBundle` 接受单官方 proof；复用现有 `AttachSourceBundle` SQL；不改 dispatch。
7. **标题**：`inventory.py` 为 missing/today 增加 `episodeTitles`；B 任务必须有 `canonical_title`。
8. **预算**：Go 任务行按 `model_used` 计数，回执对账，不做预留；`source_rule` 使用 `source:` subject；每任务 8000、每日 100000。
9. **测试**：第 14 节的 1、3、6、7、8、11、13、17、23、25、26 十一条先落地。
10. **试点**：FX → 药屋 → 罗梅莉亚 → 其余模板 → B 单官方；先影子再 enforce，只做本地验收，不发布。

### 17.2 明确不做

- 不做搜索中台、不接新的搜索 API、不做向量库。
- 不做新微服务、不做新消息队列。
- 不做前端工作台页面（先用 SQL 视图）。
- 不自动处理 C 级人工复核。
- 不做规则到期巡检，不建 90 天计时器；复用前复验。
- 不改五维验收、图片验收、读者发布、已发布章节。
- 不重写历史 `source_bundle`、不重建已登记制作任务。
- MVP 不改 `episode_source_captures` 表结构；B 证据先存 task JSONB，后续需要时再加审计列。

### 17.3 代码量级

- 1 个迁移（3 张表）。
- 约 8 个 Go/TS 文件改造 + 3 个新文件（source.queries、episode_source.go、agent source 入口）。
- 3–4 个测试文件。
- 不新增依赖。

### 17.4 MVP 通过标准

- 广州队列中待补来源的请求都生成任务，基线 124，重复 tick 不增加；20 部作品每部至少 1 集到达 `verified/done` 或给出可解释的阻塞原因。
