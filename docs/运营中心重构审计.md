# Folio AI Operations Center 重构审计

本文记录拆除前的工作台。当前状态见[功能地图](功能地图.md)。

评审稿，2026-11-22。对照《Folio AI Operations Center 产品需求文档与 UI 重构方案 v1.0》审计当前仓库。本稿只给出差距、口径和计划，不包含代码改动。结论基于源码与迁移文件；本次未连接制作库，涉及数据分布的判断需上线前用文末查询核对。

## 结论摘要

1. **数据基础比界面落后。** 生产各环节都有可追溯的 PostgreSQL 记录，但分散在十余张表、使用各自的状态词，没有统一的任务台账、Agent 实例记录、异常台账和知识资产历史快照。PRD 要求的「当前运行 Agent 数」「Blocked」「任务吞吐量」「知识资产趋势」目前无法如实计算。
2. **现有首页统计口径偏窄。** 工作台的数据只来自一个服务端函数，每类记录固定取最近 30 条（[feed.ts](https://github.com/bluedao10000/player/blob/2414d3fae5bd47c2ed9765a4510bb1d9e4ee3b53/apps/web/src/features/workbench/feed.ts) 里的 `?limit=30`）。[概览卡片](https://github.com/bluedao10000/player/blob/2414d3fae5bd47c2ed9765a4510bb1d9e4ee3b53/apps/web/src/features/workbench/dashboard/overview.tsx)的「今日成功 / 失败任务」是在这 30 条窗口里筛选的，且只覆盖来源同步与质量扫描，不含取证、出图、编辑、补集和发布。新首页必须改为服务端聚合。
3. **AI Assistant 有可用的底座。** [工作台对话](https://github.com/bluedao10000/player/blob/2414d3fae5bd47c2ed9765a4510bb1d9e4ee3b53/apps/api/internal/handler/knowledge/chat.go)已有 5 个只读工具、7 个写工具、变更提案、`expected_revision` 冲突保护和[操作审计](../database/migrations/init.sql)（`workbench_plan_operations`），前端已用 assistant-ui。缺的是跨作品上下文、更多查询工具、风险分级和统一决策记录。
4. **拓扑需要真实工作量。** [WorkflowCanvas](https://github.com/bluedao10000/player/blob/2414d3fae5bd47c2ed9765a4510bb1d9e4ee3b53/apps/web/src/features/workbench/workflow/workflow-canvas.tsx) 的节点是静态定义，节点状态用「任一条失败即失败」一类规则从记录窗口推断，没有队列数、吞吐和耗时。
5. **建议先补「只读统一视图 + 心跳 + 日快照」，再做界面。** 统一任务视图可以完全基于现有表，不改写入路径；心跳和日快照越早上线，趋势分析越早有真实历史。

### 1.3 与现有约束的冲突，需要在评审时定

- **导航语言。** PRD 一级导航用英文（Overview、Operations…），[界面文案规范](界面文案规范.md)要求工作台以中文为主、英文小标题只作视觉样式。建议中文为主名、英文作 eyebrow，例如「运营总览 OVERVIEW」。
- **「Agent」的定义。** 系统里没有可计数的 Agent 实体，只有调度车道、Pi Durable 执行和模型调用（见第 5 节口径）。PRD 的「Agent 数量」需要先确定按哪一层计。
- **访问范围。** 工作台目前只允许本机请求。PRD 第 12 节要求移动端可查看，需要决定是否放开到内网或经认证的公网入口。
- **编辑审稿入口。** PRD 要求降级为业务详情；编辑任务的人工批准是正式发布保护的一部分，降级后必须仍能从异常中心或作品详情一跳到达。

## 4. 缺少的数据统计接口

现有风格：运营只读接口挂在 `/api/v1/admin/knowledge/*`（管理令牌鉴权，`no-store`）。建议新接口沿用这一分组，加 `ops/` 前缀，不另开 `/api/v1/operations`。

| PRD 建议路由 | 已有等价或部分等价 | 结论 |
| --- | --- | --- |
| operations/overview | 无 | 新增 `GET /admin/knowledge/ops/overview` |
| operations/topology | `sync-runs`、`quality-runs`、`research-runs`、`media-candidates`（均为明细） | 新增 `ops/topology?world=`，按阶段返回计数、耗时、吞吐与最近记录 |
| operations/agents | 无 | 新增 `ops/agents`，依赖第 6 节心跳表 |
| operations/queue | `episode-queue`（补集）、`/editor/tasks`（编辑） | 新增 `ops/queue`，基于统一任务视图；`episode-queue` 保留 |
| operations/exceptions | 无 | 新增 `ops/exceptions`，依赖异常台账 |
| knowledge/summary | `world-statuses`（逐作品计数）、`/knowledge/works`（目录） | 新增 `ops/knowledge/summary`（全库汇总、类型分布、来源分布） |
| knowledge/completeness | 无 | 新增 `ops/knowledge/completeness?world=`，返回每维分子 / 分母 / 状态 |
| projects/summary | `production-usage`、`episode-inventory`、`/editor/plans` | 新增 `ops/projects`，按作品投影五态集数、预算和瓶颈 |
| analytics/production | 无 | 新增 `ops/analytics/production?range=7d|30d|90d` |
| analytics/usage | `model-usage`、`production-usage` | 扩展 `model-usage` 支持 `group_by=world|stage|operation` 与日粒度，不另建 |

所有聚合接口返回 `as_of`（计算时间）与 `definition`（口径标识），界面据此显示更新时间。

## 5. 指标计算口径

时间一律按北京时间自然日（`Asia/Shanghai`）。「—」表示当前数据无法如实计算，必须先补第 6 节对应数据。

| 指标 | 口径 | 来源 | 现在能否计算 |
| --- | --- | --- | --- |
| 作品总数 | `works.active` 的作品数；另列「已发布作品世界」= `published_worlds` 行数 | works、published_worlds | 能 |
| 作品类型分布 | `works.type` 原值：TV、MOVIE、OVA、ONA、SPECIAL、UNKNOWN；`NULL` 单列「未登记」，不归入任何类型 | works | 能 |
| 知识资产总量 | 分类分别计数，不相加：人物、章节、故事线、场景、地点、图片引用 | reader_knowledge_inventory | 能（只含已发布版本） |
| 当前执行任务数 | 统一任务视图中 `status='running'` 且未结束的行数 | 统一任务视图 | 视图建好后能 |
| 等待队列任务数 | 统一任务视图中 `pending`：补集「待准入 / 待采集」、编辑任务待执行、出图 `queued` 等 | 同上 | 视图建好后能 |
| 当前阻塞任务数 | `blocked`：前置条件不满足而无法自动推进。例：`token 预算不足`、`集数预算已满`、`等待有效盘点`、计划 `paused_reason` 非空、编辑任务 `conflict`、出图 `held` | 同上 | 视图建好后能；规则需评审 |
| 今日自动完成 / 失败任务数 | 统一任务视图中当天 `finished_at` 落在今日、状态为成功 / 失败的行数。按结束时间计，与现在按开始时间不同 | 同上 | 视图建好后能 |
| 当前运行 Agent 数 | 建议拆成两项：「在线工作进程」= 最近 2 分钟有心跳的车道与 worker；「运行中执行实例」= 当前执行任务数。不显示无法核实的「Agent 总数」 | 心跳表 | — |

## 6. 数据模型缺口

按「先只读、后写入」的顺序排列。前两项不改变任何现有写入路径。

1. **统一任务视图 `ops_task_runs`（只读视图）。** 把各执行记录投影成同一结构：`kind`（stage）、`world_slug`、`episode`、`subject`、`attempt`、`status`（pending / running / success / failed / blocked / skipped）、`started_at`、`finished_at`、`error`、`source_table`、`source_id`。来源：`knowledge_sync_runs`、`knowledge_quality_runs`、`research_runs`、`episode_capture_attempts`、`episode_configuration_attempts`、`media_steps`、`scope_acceptances`、`reader_release_attempts`、`editor_tasks` / `editor_events`、`backup_runs`。阻塞规则从 `episode_policy_queue` 和计划暂停原因映射。
2. **阶段定义表 `ops_stages`（配置）。** 拓扑节点的唯一定义：阶段编号、所属大类、上下游、对应的 `kind`。界面只读这张表画流程，计数全部来自视图，从结构上避免「用流程节点冒充工作量」。
3. **心跳表 `ops_worker_heartbeats`。** 每个调度车道、编辑 worker、Agent 进程每 30 秒写一行：`worker_id`、`role`、`node`、`version`、`last_tick_at`、`last_error`、`running`（本进程当前执行数，由 Pi Durable harness 提供）。这是「在线工作进程」和 Infrastructure 异常的唯一来源；现在循环级错误只进日志，看板无法发现车道停转。
4. **知识规则与完整度。** `knowledge_completeness_rules`（维度、必需项、适用条件、是否需要验证）和 `knowledge_completeness_results`（作品、版本、维度、分子、分母、各项状态、计算时间）。规则由人维护并入库，计算由质量扫描调度执行，不用模型打分。
5. **知识结构缺项。** 现有表只有人物、章节、故事线、场景、地点名称。PRD 要求的人物关系、组织 / 设定类型、时间线事件、人物介绍完整性都没有落点：需要 `work_character_relations`、在 `work_settings` 上增加 `kind`、新增 `work_timeline_events`。这三项会进入发布版本结构，需单独评审对已发布 slug 与锚点的影响。在补齐之前，完整度里对应维度显示「无数据」，不显示 0%。
6. **日快照 `ops_daily_snapshots`。** 每天北京时间 00:05 记录全库与逐作品的知识计数、五态集数、完整度结果。趋势图只读快照；其余趋势（吞吐、通过率、token）直接用带时间戳的明细，无需快照。
7. **异常台账 `ops_exceptions`。** 由调度根据视图和心跳生成，按 `dedupe_key` 去重：`category`、`severity`、`world_slug`、`subject`、`first_seen_at`、`last_seen_at`、`occurrences`、`auto_retries`、`status`（open / acknowledged / resolved / dismissed）、`resolved_at`、`decision_id`。AI 原因分析作为附带字段，标明模型与生成时间，不参与状态判定。
8. **决策记录 `ops_decisions`。** 把 `workbench_plan_operations` 推广到所有人工确认：提案内容、风险等级、确认人、执行结果、关联异常。旧表保留，新写入两边同步或迁移为视图。
9. **Agent 执行实例可见性。** Pi Durable 的执行状态在各节点 SQLite 中，跨节点不可见。已决定采用心跳上报（方案 A），设计见 [Phase 0](运营中心-Phase0-设计.md)。
