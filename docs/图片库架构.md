# 图片库与模型出口

广州 Axum 图片库负责 www.codeiy.com 的业务图片。浏览器通过 img.codeiy.com 访问已发布原件与签名衍生图。Nginx 走私网回源，格式转换由 libvips 完成。[广州图片服务](../apps/image/README.md) · [网关手册](../deploy/gateway/README.md)

## 数据归属与请求路径

| 数据与操作 | 当前实现 |
| --- | --- |
| 原图 | Tokio 将上传流写入独立临时目录，同时计算 SHA-256。校验类型、MIME、像素和解码后，按内容摘要分片安装对象，再提交 SQLite 记录。原图使用原始字节，重复内容可共用同一个对象。 |
| 资产目录 | SQLite WAL 保存 UUID、存储键、版本、来源、尺寸、可见性、元数据、逻辑目录和发布标记。前序版本和 AI 派生关系用 UUID 表达。目录移动和重命名只修改 SQLite。三个字符及以上的名称和元数据子串查询通过 FTS5 trigram 预筛，短查询直接匹配。 |
| 发布引用 | Gin/PostgreSQL 继续持有作品和分集的发布指针。发布接收器先公开选图并校验 SHA-256，再提交业务发布指针。图片库原子登记资产发布引用。 |
| 衍生图 | libvips 修正方向、缩放、裁剪、叠图和编码，在单独磁盘缓存内保存结果。规范化配方、源摘要、编码版本及水印摘要共同决定缓存键。相同配方并行调入会复用已生成结果。 |
| 访问与签名 | `/i/{id}` 支持流式读、单区间 Range、ETag 和条件请求。私有版本签名绑定资源路径、摘要、配方和到期时间。公开原图支持 CDN 长缓存，变体缓存一天。 |
| 安全删除 | 删除时检查公开状态、发布引用和在途 AI 输入，私有未引用资产以墓碑记录。对象继续留在卷内，异步回收待实现。 |
| 外部模型 | 新服务在 SQLite 内领取有界任务，通过 Reqwest 调用 OpenAI 及 Gemini。沿用 Agent 的 OpenAI/Magpie 出口配置约定。分析为结构化 JSON，生成和编辑结果写入原图存储并关联来源。业务预算、用量回执和 Pi 工作流继续由原服务管理。 |
| 灾备 | 备份脚本在线抓取 SQLite 快照，复制该快照引用的原图并校验 SHA-256。可重建的缓存和临时文件独立。图片签名密钥与 PostgreSQL 备份各自维护。 |

基础资源配置为 2 个解码/转换许可证、每项 1 个 libvips 工作线程、1 个 AI 工作器、2 GiB 衍生缓存。容器挂载独立数据卷。管理端需要 API Token，应用只从已登记资产读取模型输入和转换源。原图访问与 AI 供应商调用走独立的处理路径。 [API 契约](../apps/image/openapi.yaml) · [性能报告](../apps/image/PERFORMANCE.md)

参考 Imgforge 的 Axum 路由、HMAC、libvips 和缓存设计，Folio 独立实现资产目录、受控存储和签名契约。 [Imgforge 文档](https://imgforger.github.io/)

## 未来存储适配

`ObjectStorage` 提供字节与流访问、偏移读、HEAD、删除及分片枚举。未来可使用同一对象键和摘要接入新的存储后端。图片卷保持独立恢复能力。[图片技术图](diagrams/media-platform.svg)
