# 模型接入、用量与计费

知识库写作、出图、验图和判同按回执统计平台成本。私有图片试稿支持预付余额。用户确认单张最高价格，系统交付后按实际用量扣费。运营可以逐日核对供应商应付、净收入和毛利。

## 配置四条调用路径

每条路径分别设置 `*_BASE_URL`、`*_MODEL`、`*_API_KEY` 和 `*_ACCOUNT`。ACCOUNT 填稳定的供应商计费账户别名，例如 `studio-openai-prod`。共用计费账户的路径使用相同别名，轮换同一账户的 Key 时保留别名。不同账户应使用不同别名，方便对账。配置位置见[环境模板](../.env.example)和[容器映射](../compose.yaml)。

| 用途 / purpose | 配置前缀 | 实际执行 |
| --- | --- | --- |
| 分集取证与知识库写作 / content | CONTENT_AI | 数据服务调度 Pi。OpenAI Responses 接口选 `CONTENT_AI_PROTOCOL=responses`。DeepSeek 等兼容服务选 `chat-completions`，填写该服务的 URL、模型名和 Key。流式客户端请求供应商返回 usage |
| 参考图、场景图、肖像与返工 / image | MEDIA_AI | Pi 媒体步骤和独立预览 CLI 使用兼容 OpenAI Images 的生成或编辑接口。生产调度开关为 `MEDIA_WORKER_ENABLED` |
| 图片初审与复审 / vision | VISION_AI | 使用支持图片输入的 Responses 接口。初审使用 `VISION_AI_MODEL`，复审使用同一账号下的 `VISION_AI_SECOND_MODEL`，两个步骤分别计量 |
| 作品判同 / match | TYPESAFE 或 MATCH_AI | Gin 管理接口按既有路径执行。Jev 选 `MATCH_AI_PROVIDER=typesafe`，使用 `TYPESAFE_*` 调用 `/systemone`。也可选 `openai` 用 `MATCH_AI_*` 配置 Chat Completions |

可在各服务分别填写同一把有相应权限的 Key，也可以独立轮换。内容和视觉在未指定自定义地址时兼容历史研究 Key；显式指定地址后要给对应路径设置 Key。Jev 的 Key 只给执行判同的 API 服务。配置变更用 `docker compose up -d` 应用。H5 无需模型凭据。

## 一张候选图怎样记账

假设第一次出图后，初审发现裁切问题并启动视觉复核。这会分别留下出图、初审和复审三次请求，关联媒体槽位、轮次、步骤和业务尝试号。若随后只用本地工具重新裁切，就没有新的模型用量；若重新出图，则增加一次图片请求。判同直接复用已保存结论时同理。供应商已返回用量后，即使 PNG 解码或结论校验失败，仍计入生产消耗。

1. Pi 在发送 HTTP 前把调用 UUID 和任务身份写入持久卷里的 SQLite 发件箱。收到 JSON 或流式回执后，追加结束事件。数据服务分批写 PostgreSQL，提交成功后才向 Agent 确认。进程重启或确认丢失均可重送。
2. Go 判同先独立登记请求，再访问供应商。最终回执使用独立上下文写入，即使治理事务回滚也能保留。回写暂时失败时保存至归档卷中的 `model-usage-outbox`，常驻数据服务回放。独立预览命令离线时回执保存在系统用户缓存的 `tidepost/model-usage-outbox`，有数据库连接时可执行 `knowledge usage-import --dir <回执目录>`。
3. 表 `model_calls` 保留每次 HTTP 尝试，包括重试。视图 `model_usage_receipts` 在相同端点与供应商账户内，优先使用供应商响应 ID，再使用请求 ID 关联重复回执。没有供应商 ID 时以本次调用 UUID 区分。图片请求携带的幂等键可辅助查账，单靠该键无法证明供应商只扣过一次费。
4. 同一回执只汇总一次。收到相互冲突的输入、输出、总数等记录时保留原始尝试，标为 `inconsistent`。崩溃可能发生在供应商已执行、客户端尚未收到回执的间隙，`started` 或 `unknown` 会保留以待核对。若供应商既不提供回执 ID 也不提供历史账单明细，系统无法保证跨请求识别所有重复扣费。

持久记录含账户别名、配置端点、请求与返回模型名、任务身份、HTTP 状态、时间和用量。用量字段只保留数值与数值分项，账本排除 Key、提示词、正文和图片内容。[账本迁移](../apps/api/internal/knowledge/sql/029.sql) · [Pi 采集](../apps/agent/src/model-api.ts) · [Go 持久化](../apps/api/internal/modelusage)

## 怎样读用量

| 回执状态 | 解释 |
| --- | --- |
| measured | 上游报告总量，或提供了可相加的输入和输出。明确返回的零保留为零 |
| partial | 只有部分 token 计数，已知分项保存在明细中 |
| unreported | 请求已结束，供应商没有提供可识别的 token 总量或输入输出分项 |
| unresolved | 没有完整的调用结果，实际消耗需要核对 |
| inconsistent | 同一回执的数字有冲突或与其分项合计不符，需要核对 |

汇总取去重后的 measured 记录。输入和输出或供应商细分项缺失时保留空值。缓存、推理、图像与文本 token 可能是输入或输出的子集，重复相加会高估消耗。图像同时保存返回张数、请求尺寸和指定画质。例如接口成功返回一张图却省略 usage，查询会显示一张图及未知 token。上线前的历史任务没有逐次回执，保留其既有业务记录。

管理员可用以下命令查询。运行前把管理 token 放在当前环境中，基础地址可由 `KNOWLEDGE_API_URL` 指定。

```sh
usage_url="${KNOWLEDGE_API_URL:-http://127.0.0.1:4321}/api/v1/admin/knowledge/model-usage"
curl -fsS -H "Authorization: Bearer ${KNOWLEDGE_ADMIN_TOKEN}" "$usage_url"
curl -fsS -H "Authorization: Bearer ${KNOWLEDGE_ADMIN_TOKEN}" \
  --get "$usage_url/calls" --data-urlencode "subject=research:${RESEARCH_RUN_ID}" --data-urlencode 'limit=20'
```

汇总默认最近 30 天，按用途、供应商端点、账户和实际模型分组。可用 RFC3339 的 `from`（含）与 `to`（不含）指定结算窗口。汇总按同一回执最早的请求时间归属，跨日重送只计入原窗口；调用明细按各次尝试的时间过滤。`duplicates` 为重复回执次数，`unmetered` 为未纳入 token 合计的唯一回执数，`unresolved` 统计状态未确定的实际尝试。明细用上一页最小 `seq` 作下一页的 `before`。回执明细可查看缓存、推理、图像等供应商实际返回的数值。[管理 API](../apps/api/internal/knowledge/usage.go)

本地验收尚未启用管理账户时，可以直接用数据库只读查询观察计量。下面按用途列出去重回执数、缺失或冲突回执数，以及可核实的 token 合计。空账本返回零行。

```sh
docker compose exec -T postgres psql -U anime -d anime_knowledge -c "
  SELECT purpose, count(*) AS receipts,
         count(*) FILTER (WHERE meter_state <> 'measured') AS needs_review,
         sum(total_tokens) FILTER (WHERE meter_state = 'measured') AS tokens
  FROM model_usage_receipts WHERE receipt_rank = 1
  GROUP BY purpose ORDER BY purpose"
```

本机 Compose 的 Agent 仅在容器网络内提供回执读取与确认。备份应包括 PostgreSQL、Agent 状态卷和归档卷；独立 CLI 的离线缓存另行备份。双云拆分时，确保回执写入方所在机器的磁盘可由恢复任务读取，跨主机的内部接口使用服务身份认证和加密传输。[运维手册](运维手册.md)

## H5 读者购买与验收

读者从「我的书架 → 我的约稿」进入，使用开通预付账户时收到的访问码登录。填写角色、外观、场景、画风和画幅后，「核对约稿」显示实际提交的创作说明、币种与单张最高扣款。「确认预留」才会建立订单。排队期间可以取消，交付后在同页下载 PNG、查看实扣和余额流水。[本地约稿页](http://127.0.0.1:4310/commissions)

运营先按下表开通账户，读者可通过支付宝充值，也可由运营登记线下到账凭证，再登记与图片端点、账户别名、模型完全一致的零售价。启用履约进程的命令如下。真实订单会调用供应商并产生费用。

```sh
docker compose --profile reader-sales up -d --build api sync reader-orders
```

`reader-orders` 每 15 秒报告可用性。匹配报价的进程超过 45 秒未报告时，H5 新单暂停，提交端也会检查。暂停接单可执行 `docker compose stop reader-orders`。重启后继续领取已预留的 H5 订单，生成中断的记录沿用下面的恢复与取消流程。服务端直接用长期账户凭证建立的订单保留按单履约方式。

浏览器通过同源 `/reader-api` 访问账户，仅保存 12 小时有效的 HttpOnly、SameSite=Strict 会话 Cookie。公网部署使用 HTTPS，并让 H5 看到与浏览器一致的请求 Origin；本机 loopback 支持 HTTP。退出时 Gin 撤销会话。生产管理凭证只用于管理 API。H5 当前支持预付余额，运营通过管理接口开户。

## 支付宝手机网站充值

「我的书架 → 我的约稿 → 余额充值」面向人民币账户。读者输入以元表示的金额，确认后前往支付宝收银台。单笔支持 0.01 至 10,000 元，付款窗口为 30 分钟。返回约稿页可查看余额和最近 20 笔充值记录。「待支付确认」表示系统正在等待渠道通知，刷新页面会重新读取账本。

| API 服务的环境变量 | 填写内容 |
| --- | --- |
| `ALIPAY_APP_ID` | 已签约手机网站支付的支付宝应用 App ID |
| `ALIPAY_PUBLIC_KEY` | 支付宝公钥，用于验证异步通知 |
| `ALIPAY_NOTIFY_URL` | 本项目对外的 HTTPS 通知地址，如 `https://www.codeiy.com/api/billing/alipay/notify` |
| `ALIPAY_PRIVATE_KEY` | 与该应用登记公钥配对的应用私钥，支持 PKCS#1、PKCS#8、PEM 或 Base64 |
| `ALIPAY_SELLER_ID` | 签约收款账号对应的卖家 ID |

五项配置齐全后执行 `docker compose up -d --build api`。H5 服务也须部署对应版本。当前使用公钥模式、RSA2 签名和正式网关。未配置时账户仍可使用已有余额。通知地址使用 H5 的公网域名，支付返回地址取同域的 `/commissions`。该域名上的 `POST /api/billing/alipay/notify` 由 H5 转发或由反向代理直接送至 Gin。若入口改写路径，须转发到 Gin 的同一处理器。私钥仅由 Gin 读取。

Gin 用 `alipay.trade.wap.pay` 签发收银台请求，产品码为 `QUICK_WAP_WAY`。浏览器返回只读取状态。收到支付宝通知后，Gin 验证签名、App ID、卖家、商户订单号、渠道交易号和原单金额，在同一个 PostgreSQL 事务内保存支付结果与余额流水。金额以整数分校验，1 分记为 10,000 微元。同一交易重复通知只能入账一次，通知晚于本地支付窗口时仍可据实确认。支付宝充值本金、试稿扣费和试稿退回余额分别入账。支付宝渠道原路退款及渠道退款后的自动冲账待接入，相关通知会保留错误日志并返回失败以便复核。

本地回归可运行 `go -C apps/api test ./internal/knowledge -run TestAlipayWapTopup -count=1`，需设置隔离测试数据库连接。测试使用临时 RSA 密钥核验商户下单签名、通知验签、重复入账和冲突通知。真实渠道验收需在本项目公网回调可达后，用已签约商户完成小额实付，核对商户后台交易号和本地余额流水。[支付实现](../apps/api/internal/billing/alipay.go) · [通知回归](../apps/api/internal/knowledge/alipay_test.go)

## 用户如何为一张私有试稿付费

账户固定使用一种币种，所有金额以整数微单位表示。以人民币为例，`1000000` 表示 1 元。余额是已入账流水之和，可用余额等于余额减去未结订单的预留额度。用户授权、生成和结算可以在不同时间发生。

| 步骤 | 接口或命令 | 可以核实的结果 |
| --- | --- | --- |
| 开户 | 管理端 `POST /accounts` 传 `customer_ref`、`currency`、`token_sha256` | 为每个账户生成独立的高熵随机 Bearer token，例如用 `openssl rand -hex 32`；入库的是原始 token 字符串的 SHA-256 十六进制摘要。购买端使用原始 token |
| 登记到账 | 管理端 `POST /accounts/:id/credits` 传 `reference`、`currency`、`amount_micros` | reference 使用唯一到账凭证。相同凭证重复提交只入账一次，变更金额或账户返回 409。记录为预付额度，实际资金到账由支付渠道或线下凭证确认 |
| 查价与授权 | 用户 `GET /quote`，再 `POST /orders` | 报价含费率 ID 和 `cap_micros`。新订单锁定报价、尺寸和创作说明，并预留上限。额度不足返回 402，报价过期返回 409，同一账户以相同请求和 `client_key` 重试取得同一订单 |
| 生成与交付 | H5 订单由履约进程领取，API 手工订单使用下方命令 | 单张原创 PNG 进入账户私有目录。交付文件和回执齐全后只扣一次，实际扣款取计价结果与授权上限中的较小值，释放剩余额度 |
| 查账与取图 | 用户 `GET /account`、`/entries`、`/orders/:id` 和 `/orders/:id/image` | 明细包含已用计价单位、收费前原价和最终扣款。只有对应账户在订单结算后可下载。订单列表和流水各自支持 `before` 游标 |
| 取消与退款 | 用户 `POST /orders/:id/cancel`；管理端 `POST /orders/:id/cancel` 或 `/orders/:id/refund` 传 `reason` | 用户可取消尚未执行的订单。运营可以关闭无法交付的未结订单并释放额度。已结订单支持全额退回原余额，原扣费与退款分别保留 |

用户路径前缀为 `/api/v1/billing`，管理路径前缀为 `/api/v1/admin/knowledge/billing`。两侧分别使用账户 token 和既有的知识库管理员凭证。试稿为当前计费商品，H5 公开阅读与平台选题自动取证、出图、返工按原有方式运行。H5 购买与直接 API 下单共用同一账户、费率与流水。

用户下单请求示例。把 `rate_id` 换成该账户最新报价返回的 UUID，为同一次购买保留相同的 `client_key`。

```json
{
  "client_key": "pier-illustration-01",
  "rate_id": "<报价中的 rate.id>",
  "request": {
    "size": "1024x1536",
    "brief": {
      "original_subject": "夜班渡口的原创引航员",
      "visual_bible": "靛蓝外套，银色船灯",
      "scene": "等最后一艘渡船靠岸",
      "composition": "人物居中，底部留出手机标题区",
      "art_direction": "雨夜水彩"
    }
  }
}
```

在本地 Compose 中执行已授权的订单。该命令会调用配置的图片供应商并可能产生实际费用。

```sh
docker compose --profile billing-tools run --rm media-preview --order "$ORDER_ID"
```

订单依次经过 `reserved`（已预留）、`running`（生成中）、`delivered`（文件已交付待结算）、`settled`（已扣款）。取消和已确认的生成失败进入 `void`，全额退款进入 `refunded`。命令重跑时检查既有结果。数据服务回放用量回执，并为已落盘的试稿核验摘要、补做结算。进程在供应商执行后、图片落盘前中断时，订单可留在 running；运营可查回执后取消并释放预留。备份需覆盖 PostgreSQL、归档卷内的私有图片和回执。

## 运营如何定价

管理端 `POST /rates` 追加版本，`GET /rates` 查历史。上线需登记实际合同成本与自主零售价，迁移不会预填金额。在首个零售价生效之前，账户查价返回 404。

| 字段 | 填写方式 |
| --- | --- |
| `kind`、`endpoint`、`provider_account`、`model` | `retail` 选择履约端点、计费账户别名和请求的模型。每币种当前提供一种私有试稿报价。`cost` 按供应商端点、账户和回执所报模型的组合配置，模型缺失时使用请求名 |
| `currency`、`effective_at` | 三位大写币种、含时区的 RFC3339 时间。成本按调用开始时生效的版本计算。追溯补录成本价会重算所覆盖期间的本地应付；已结的用户订单保存原费率与金额 |
| `unit`、各单价 | `total_tokens` 的 `unit_micros` 是每百万 token 价格。`split_tokens` 填每百万输入、输出的 `input_micros`、`output_micros`，可另填缓存输入价 `cached_micros`。缓存属于输入的子集。`image` 的 `unit_micros` 是每张价格 |
| `cap_micros` | 零售价必填正数，表示该单最多可扣多少。成本价使用零或省略。金额在每份去重回执上合计后四舍五入到一个微单位 |

例如测试中 11 个输入 token 含 3 个缓存 token，另有 2 个输出。假设普通输入、缓存输入、输出每百万 token 分别为 2 元、1 元、3 元，则本单计得 25 微元。若回执只给出总数，按总 token 定价的订单可结算，要求区分输入输出的订单会等候补全。合同若对尺寸、画质或不同模态分别计价，须先扩展费率规则才能按该合同上线。

## 怎样核对每日账单

1. 将供应商账单按 **UTC 日期 × 端点 × 计费账户 × 模型 × 币种** 汇总。管理端 `POST /statements` 提交 `day`、`endpoint`、`provider_account`、`model`、`currency`、`amount_micros` 和原凭证 `reference`。账单修订使用新 reference，并以 `replaces` 指向本组上一条凭证。可重复导入同一行。
2. 查 `GET /reconciliation?day=YYYY-MM-DD&currency=CNY`。每组同时展示去重回执数、待核回执数、已知成本、供应商金额与销售净额。差额等于供应商金额减本地应付。
3. 差额或待核项可下钻 `GET /reconciliation/receipts`，使用同一日期和币种，可按 `provider_account`、`model` 过滤，以 `after` 传上一页最后一个 call_id。用 `GET /statements` 核查该日所有原始和修订凭证。
4. 对于用户订单，用 `GET /orders?status=delivered` 查看待结订单。文件缺失、用量不全、相同回执跨订单或计量矛盾时，先补核供应商记录。数据服务会重试，也可调用管理端 `POST /orders/:id/settle` 重试。取消未结订单或退回已结金额均需填写原因。

| 日账状态 | 含义 |
| --- | --- |
| matched | 已知本地成本与供应商同组金额一致 |
| difference | 两侧金额都有，存在差额 |
| pending | 成本费率、用量或归属还需补核 |
| local_only / supplier_only | 仅一侧有记录，需要补账或核对分组 |

毛利在已匹配且收入币种可比时给出，等于同组用户净收入减供应商金额，含平台制作成本。退款回溯至原服务日，因此历史毛利会反映后续退款。报表直接读取已导入的供应商日账及最新有效修订。支付宝渠道账单下载与原路退款、自动拉取各模型供应商账单、跨币种折算属于后续接入范围。
